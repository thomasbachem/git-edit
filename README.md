# Fast, efficient, and safe Git history rewrites for AI agents

An AI coding agent that commits as it works keeps rewriting what it committed – folding in a fix, rewording, splitting, reordering – with nobody at the keyboard, and often with other sessions working in the same checkout. `git rebase -i` is built for a person at an editor, so the agent hand-rolls each rewrite: a scratch worktree, a scripted todo list, a compare-and-swap onto the branch, an index re-sync. That's five or six calls on the happy path, each a model turn, and one slip from reverting another session's commit. `git edit` makes it one call:

```
git edit <commit>                                     # edit that commit's content
git edit -M --text="Better subject" <commit>          # reword it, working tree untouched
git edit -M --subject="Better subject" <commit>       # or change its subject alone, the body kept
git edit -d <commit>                                  # drop it
git edit HEAD~2..HEAD                                 # squash all three into the oldest – ranges include both ends
git edit --amend-into=auto                            # fold staged changes into the commit that owns the lines
git edit --split=<commit> --text="Icons" -- src/svg/  # cut the icons out into a commit of their own
git edit --move=<commit> --after=<anchor>             # slot a commit where it belongs
git edit --land=feature                               # land a finished branch on the checked-out one
git edit --undo                                       # take the last operation back
```

What it's good at:

- **Leaving your checkout alone.** The plumbing modes never check anything out, and the rest work in a throwaway worktree, so history can be restructured with uncommitted work sitting right there, yours or another session's. Once a run lands – an agent's or a person's at a terminal alike – it brings the checkout it started in along: a file nobody touched takes what landed, uncommitted edits merge onto it, and where they would conflict the file stays as it was, the `git merge-file` command that brings the markers in named for whoever owns those edits – nothing is overwritten, and in the normal case nothing is left to run. Where it can't, a checkout halfway through a merge say, it names the one `git edit --carry` that does, never a `git restore`, which run later would take an edit another session made since.
- **Sharing a checkout with parallel sessions.** Every ref move is a compare-and-swap and nothing is consumed until it lands, so a commit another session lands meanwhile is never overwritten, and a failure or `--abort` leaves nothing to roll back. Folds take `-- <paths>`, since a peer can stage into the shared index mid-call, and a commit or fold takes just your own lines from a file another session is also editing – `--edits` replays the replacements you made onto the tip's content, leaving theirs out.
- **Being driven by an agent.** One call per intent, a closing status line to dispatch on, stale SHAs that resolve to their rewritten identity, refusals that name their fix – and guards against the ways agents fail, like staged conflict markers or a marker-less conflict read as resolved.
- **Folding a fix into the commit that owns the lines.** `--amend-into=auto` finds it by blame, then folds in isolation – gated by your test suite, if you pass `--verify`.

Pushed commits are refused unless you pass `--allow-pushed`, merge commits are rebuilt faithfully or refused but never flattened, and `git edit --undo` takes back the last operation.

## Installation

```
brew install thomasbachem/tap/git-edit
```

Or clone the repo and add the folder to your `PATH`, e.g. by adding this line to `~/.zshrc`:

```
export PATH="$PATH:/your/path/to/git-edit"
```

Either way `man git-edit` works right away – the formula installs the page, and on the `PATH` route `man` derives `<dir>/man` from each entry and finds the bundled `man/man1/git-edit.1`. Needs `zsh` and `git` 2.31+, `--snapshot` 2.40+ – `git replay` (2.44+) rebuilds linear spans in one pass where it exists, and is never required. Below 2.42 git can't tell a sparse checkout's patterns, so files a rewrite adds there are left out as maybe outside it, named with the `git sparse-checkout reapply` that writes the rest.

## The modes

`git edit -h` prints the full flag reference, `man git-edit` the details behind each of these.

| | |
| --- | --- |
| `git edit <commit>` | **Edit** its content. Pauses for your changes, then amends the commit and replays the descendants |
| `git edit -M <commit>` | **Reword** only – pure plumbing, no checkout. `--text` skips the editor, `--subject` replaces the subject alone and keeps the body byte for byte |
| `git edit -d <commit>...` | **Drop** commits or ranges. Their content leaves your checkout too, edits on it kept, the run naming the way back – `git edit --undo` while it is the last run, else `git show <old tip>:<path>` |
| `git edit -s <commit>...` | **Squash** into the oldest of them, a single commit into its parent – `-s=<target>` into a named one, `-S` to demand the plumbing path instead of a rebase fallback |
| `git edit --amend-into=<sha>` | **Fold** the staged changes into a past commit |
| `git edit --commit --text <msg> -- <path>...` | **Commit** files whole from the checkout, as `git commit -- <paths>` does – composed apart from the shared index, at the tip or, with `--after=<anchor>` or `--before=<anchor>`, right beside that commit |
| `git edit --split=<sha>` | **Split** one commit into two |
| `git edit --reorder <commit>...` | **Reorder** a contiguous span, the arguments giving the new order oldest-first |
| `git edit --move=<sha> --after=<anchor>` | **Move** one commit (`--before=<anchor>` likewise) – span and ordering derived |
| `git edit --move=<a> --move=<b> --after=<anchor>` | **Move several** as one block in one replay, commits between them staying put – `<oldest>..<newest>` names a run |
| `git edit --onto=<upstream>` | **Replant** the branch onto a moved upstream |
| `git edit --land=<branch>` | **Land** another branch's commits on the checked-out one – a fast-forward where it can, else a replay onto the tip in a worktree of its own, of the commits the checked-out branch never held by its reflog (`--base=<sha>` names another fork) – with uncommitted work in the checkout left as any landing leaves it, and `<branch>` itself never moved |
| `git edit --exec -- <cmd>...` | **Anything else**, run in an isolated worktree – in its copy of the directory you call from, `GIT_PREFIX` naming it, a relative program path read from there as the shell reads it – and applied only if it moved HEAD |

Edit is the default mode, and `-e` / `--edit` names it – which refuses a second commit where the bare form would take two as a squash. The other short flags have long spellings too – `--reword`, `--drop`, `--squash`, `--resquash`, `--message`, `--dir`, `--yes` – and mode and flags can be given in any order. A range `A..B` includes both its ends, unlike git's own. Every mode needs a checked-out branch but `-M`, `-S` and a split by pathspec.

## Folding staged changes into a past commit

```
git add src/foo.js
git edit --amend-into=<sha>                          # fold what's staged into that commit
git edit --amend-into=auto                           # or let it find the commit those lines belong to
git edit --amend-into=<sha> -- src/foo.js            # fold only these staged paths, leave the rest staged
git edit --amend-into=<sha> --text="Better subject"  # fold and reword under one ref update
git edit --amend-into=<sha> --tree=<tree-ish>        # fold a tree composed apart from the shared index
```

`auto` resolves the target from the folded **lines** – staged, or composed by the inputs, `--whole` or `--tree` – rather than the files, because a fix belongs to whoever wrote the line being fixed. Take a file where commit A added one rule and B and C later added and refined a second one: editing A's rule makes C the newest commit touching the *file*, while A still owns the *line*. Where those lines point at several commits, or at a pushed one, it refuses and names the candidates instead of picking a winner. A purely additive hunk has no old line to attribute, so it falls back to the newest unpushed commit touching the staged paths – and refuses just the same where the paths disagree, or where every one of them is new. A submodule's pointer has no line at all, so a fold carrying one refuses `auto` – name the commit it belongs with.

Only staged changes are folded, and nothing is consumed until the final compare-and-swap – on a conflict or an `--abort` they are simply still staged, ready for the retry. The pathspec form is worth reaching for whenever the index might hold more than you mean to fold: in a shared checkout a parallel session can stage into it between your `git add` and the call. A pathspec that names a staged path is that path alone, even one git would read as a pattern or as magic – `app/[id].tsx`, `:notes.txt` – while magic given outright (`:(…)`, `:/`, `:!`, `:^`) stays as given. A staged path the target predates is refused where a later commit introduces it, since folding beneath that introduction turns every descendant touching the file into an add/add conflict – `--allow-new-path` overrides – and so is a removal folded there, with no override, as that later commit brings the path back. A path renamed since folds onto its old name instead, wherever git's rename detection pairs the two as the replay's own merge will, and a note names the old path. Where it does not – later edits outgrew the old content – but the commit the path arrives in renamed it, the refusal of a path the fold keeps names the old path and that commit, and the edit pause that works: `git edit <sha>`, the change made to the old path in its worktree, then `git edit --continue`. A flipped file mode is refused as well, unless `--allow-mode-change` says it is meant: a fold rarely means one, and the usual cause is a literal mode typed into `git update-index --cacheinfo`, which takes the executable bit with it and would ride into history invisibly, a diffstat counting lines only. The guard holds through the replay: at a conflict stop, `--continue` refuses a staged resolution that leaves a path at a mode neither the replayed commit nor its new parent carries – the way a file written anew into the worktree and staged comes back, without its executable bit – and names the `chmod` and `git add` that restore it, worktree and index both; and the landing refuses a tip carrying a mode change nothing asked for, naming the rebuilt commit that brought it in. `--allow-mode-change` on the continue keeps either.

Where later commits rewrote the lines beside the fold, a replay stops at each of them for a state written by hand. A fold given as `--edits` alone resolves those stops itself: where the commit a stop builds holds each old text exactly once in every conflicted file – a renamed file under the name it had there – the file takes the edits in that commit's own content, what it holds with the fold made in it, and the replay goes on. It pauses as before at the first stop where that commit holds an old text other than once – one that changed that text – and leaves the stops after it to the resolver. `--snapshot` merges the fold into every commit from the target up instead – each through `git merge-tree` against the pre-op tip, so a file moved since takes the fold under its old name – and keeps each commit's author and message. A conflict stops once per distinct content of its file, in a worktree laid out as any merge's, and that resolution serves every commit carrying the same, while rerere pre-fills a hunk already resolved at an earlier stop. Only a conflict over content resolves this way – a rename or deletion meeting the fold refuses, as does `--text`.

Where the shared index is itself the hazard – a parallel session's uncommitted edits sit in the very file you are folding – `--tree` takes the fold's content from a tree composed apart from it: seed a private index from `HEAD` (`GIT_INDEX_FILE=… git read-tree HEAD`), place your blobs at `HEAD`'s modes, `write-tree`, and hand the result over as a commit on `HEAD`, which pins the tip it was composed on, so a tip that moved since is refused rather than have the diff carry a newer commit's reversal. The shared index is neither read nor written – its entries are reconciled afterwards as any rewrite's are, re-synced where they still hold the pre-op tip and named where they don't.

## Committing whole files

```
git edit --commit --text "Subject" -- src/foo.js src/new.js   # commit these files as they stand
git edit --commit --text "Subject" --after=<sha> -- src/foo.js # or land the commit beside the run it continues
git edit --amend-into=<sha> --whole -- src/foo.js             # or fold them whole into a past commit
```

`--commit` takes files as `git commit -- <paths>` does, though only named one by one, no directory or glob – each as it stands, a new one with no `git add`, a deleted one removed, a moved one named at both paths – into a private index seeded from `HEAD`, read through the files' filters as `git add` reads them, and refuses a file carrying conflict markers its tip version lacks. It lands the commit the way `--exec` lands its result: the repo's hooks run on it whatever `--no-verify` says, `edit.verifyCmd` unless `--no-verify` skips it, the branch moves only from the tip the files were composed on, and the journal and reflog name the caller. Files staged beside them stay staged and out of the commit. A file-mode change refuses unless `--allow-mode-change` says it is meant. A submodule records no pointer this way, so it refuses, naming the run that does – an `--exec` setting the pointer at the tip, or `git add` and a staged fold for `--whole`.

With `--after=<anchor>` or `--before=<anchor>`, the commit lands right beside that commit instead of at the tip, in the same run – built on the tip, then replayed into place in the run's own worktree, so the branch never holds it at the tip, no second command moves it, and the gate checks it where it lands. A conflict placing it pauses as `--move` does, with nothing landed, and a pushed commit or a merge above the anchor refuses before anything is built. `--exec` takes the same flags for the commits its command adds on top.

Where a file you changed also holds another session's uncommitted lines, taking it whole would take those too. The inputs compose the commit from your own changes alone instead, on the tip's content in a private index – `--edits` replays replacements you made by hand, each old text matching exactly once so a peer's line inside it refuses rather than merging (in the text the commit stores – under a clean/smudge filter an old text copied from the checkout refuses, naming the filter and `--put`), and in order, so one whose match an earlier edit of the same file rewrote refuses, naming that edit to merge it with; `--patch` applies hunks you split, `--put` replaces a file with one you rebuilt from `git show <sha>:<path>` – the route for a file rebuilt or derived from a diff – `--chmod` and `--rm` set a bit and remove a path. Every path an input changes is checked against other callers' landings as whole files are, as edits or a patch built from a checkout file that predates one take it back all the same – or, more exactly, against the commit you built it from, named by `--base`, refused where that path changed since; never `$(git rev-parse HEAD)` in the same call, which only checks the tip against itself. Files wholly yours go after `--` beside the inputs, each taken exactly as `--commit -- <paths>` alone takes it – the same checks and guards, a file the checkout lacks removed, its index entry re-synced – rather than rebuilt as an input from `git diff HEAD`, which would take back a landing the file lacks; a path an input names too refuses, naming both. `--amend-into=<sha>` takes the same inputs to fold them, files taken whole beside them after `--whole`, and `--commit --tree=<commit>` lands a commit composed on the tip by anything else, no paths beside it.

```
git edit --commit --text "Subject" --edits '{"src/app.js": [["old line\n", "new line\n"]]}'
git edit --commit --text "Subject" --edits=edits.json -- src/mine.js src/new.js   # edits, and files wholly yours
git edit --amend-into=<sha> --patch=fix.patch --put=src/new.js=/tmp/new.js
```

A checkout other callers share has one more way to lose work: a rewrite one of them lands – a drop, a fold built elsewhere – changes a file at the tip, and though the run brings the checkout along, a file still edited on the old content – a conflict its sync left, an editor's buffer read before it, a checkout it couldn't bring along – and committed whole takes that change back. `--commit`, `--whole` and a fold of what is staged or of a bare `--tree` refuse where a file lacks what another `GIT_EDIT_ACTOR` caller's run of the last 7 days landed on it and the tip still carries, would bring back a file such a run removed or remove one it added or edited – naming the run and the remedy: `git edit --carry=<old tip>` to merge edits onto what landed, a rename's too, from the earliest such run the file lacks, one on its old name before a run renamed it into place, or by that run itself, included, so one carry takes in every run since, a file you moved to the new name by hand moved back first where nothing stands at the old name, in the checkout or at the tip, else merged into the new name with the `git merge-file` named – for a fold of what is staged, a `git add` after it where the checkout file holds just what you staged, else the staging rebuilt alone with what landed merged in (a `git merge-file` and a `git update-index --cacheinfo` at the entry's mode), or, where your staging conflicts with what landed, a replay with `--edits` or `--patch` – a file the landing renamed unstaged first and staged again under its new name – a `git restore` where the file holds no edits of its own or is one the run added – `--staged` for a fold of what is staged, which takes what landed – and leaving out one it removed, or renamed to a path a later run removed. Runs under the caller's own label never count – for an unlabeled caller, every unlabeled one – nor do edits made on the landed lines afterwards, which conflict rather than merge. A rename of your own made on a file such a run changed refuses too, naming the `git merge-file` that brings what landed into the new name. A file another such run added counts as taken back where yours stands in its place – one keeping most of its lines, or of the tip's since, is edits on top. `--base=<sha>` names the commit the files rest on instead, refusing any path changed since – the tip's own SHA where taking a landing back is the point.

## Rewording a whole span in one pass

`-M` with no commit named reads `--- <commit>` records from stdin instead – exactly the shape `git log` emits, so the flow is dump -> edit -> feed back:

```
git log --format='--- %h%n%B' origin/main..HEAD > msgs.txt   # every unpushed message, batch-shaped
$EDITOR msgs.txt                                             # fix the bodies that need it
git edit -M --text - < msgs.txt                              # a record left unchanged is skipped
```

One walk rebuilds the span under a single compare-and-swap, where N separate rewords would replay the tail N times and open N ref-move windows. Every tree is reused verbatim, and the batch is all-or-nothing: an unreachable, already-pushed, empty or duplicated target aborts it before an object is written.

## Splitting a commit

Name one half by pathspec, and the split is pure plumbing – the trees are composed from the original blobs, so no conflict is possible:

```
git edit --split=<sha> --text="Extracted: the icons" -- src/svg/
```

Where both halves live in the **same file**, no pathspec can name them apart. Drop it, and the split pauses with a worktree holding the commit's own content: edit it back to what the first commit should leave behind, then `git edit --continue`. Authoring that one intermediate state is the whole description of a hunk-level split, and it is one a non-interactive caller can give without `git add -p`. A file mode neither the commit nor its parent carries is refused the way a path the commit never touched is – a file written anew into the worktree comes back without its executable bit, and the remainder would flip it straight back; `--allow-mode-change` keeps it.

Either form inserts the new commit **beneath** the target and leaves the target above it with its own tree, message and identity – so `--text` always names the inserted commit, and the remainder keeps a subject written for the whole change, body included. Reword it afterwards with `git edit -M` – `--subject` replaces its subject and keeps the body, while `--text` replaces the whole message, so restate the body lines that still hold, and the run names any it finds missing.

## Replanting onto a moved upstream

```
git edit --onto=main
```

The point of the mode is that it derives the fork point instead of asking for it. `git rebase --onto main <old-base> <branch>` needs `<old-base>` spelled out, and after a rewrite of `main` that commit is orphaned – so the caller has to have tracked the pre-rewrite SHA. `--onto` recovers it from `main`'s reflog, and says so when it has to fall back to a plain merge base.

It reports the triage up front: what the upstream gained, and which of your commits it already carries by patch id. Those are dropped by the replay and counted again in the summary, since a shorter branch that isn't accounted for reads as lost work. A commit the upstream took a *different* way conflicts, and `git edit --skip` steps over it rather than duplicating the change. A replant genuinely changes the branch's content, so your checkout is brought along with it – which is why uncommitted work on a path the upstream changed since the fork is refused up front, before anything moves, each path named with its next step: commit it if it is yours, else wait for the session whose work it is. Work on the branch's own files rides along as it is.

## Landing a finished branch

```
git edit --land=feature --dry-run     # fast-forward or replay, and which commits
git edit --land=feature               # land them on the checked-out branch
git edit --carry=<old tip>            # where a land could not bring the checkout along, as it names
```

Sessions sharing one checkout finish their branches into its `main` while it holds other sessions' uncommitted work – by hand that's a temp commit and a raw `git rebase`, or an `update-ref`, outside every guard. `--land` does it in one call. The branch's own commits are those `main` never held – not reachable from its tip or any value in its reflog, set aside what an `--undo` took back: the commits each land it took back brought, whatever that land named – a land of `feat~1` counts for `feat` – and their copies a rewrite of `main` made meanwhile, a peer's commit made and taken back there staying held – and its fork is the first commit with none of them at or below it. So a land taken back, the branch then redone or moved onto the copies a replay landed, a catch-up by merge, pull, land or `update-ref`, or a peer's reword, fold or drop below the fork never shrinks the span or brings back what `main` dropped. What lands is those commits alone: a commit `main` held and dropped since stays out of the replay by name, the drop standing, even one between the branch's own, as does one that is `main`'s by a land's own record – a copy a catch-up land of `main` into the branch made – each commit `main` holds or held pairing with one at most, by the author name, email and date a replay keeps, else by its whole message after git's comment and whitespace cleanup, as a resolution committed by hand at a stop keeps it, so a commit made in that land's pause stays the branch's own – or another branch's commit whose change and message `main` holds in a copy a land of that branch brought. Inside a merge, a catch-up merge's say, no replay can leave such a commit out, so that refuses, naming the `--base` past it – never a merge, nor a `--base` ending in the merge refusal – and a fast-forward happens only where nothing stays out. Whether one of the branch's own commits landed is never guessed: one that looks like a copy of a commit `main` holds or held – the same author name, email and date, and the same subject or patch, as a replay, pick or rewrite leaves one – refuses the whole land, naming each with its lookalike and a step for each that needs one, every step landing as printed: where `main` lacks its change, the `--amend-into=<sha> --tree=<commit>` that folds that change alone into `main`'s copy, even one `main` reworded since – the first such fold alone, as each moves the tip the next is composed on; where it lacks the message, the `-M --subject=…` – or where more than the subject differs, the `-M --text="$(git log -1 --format=%B <commit>)"` – that rewords it; where `main` dropped the lookalike, the `--exec -- git cherry-pick` landing it back; where each copy on `main` carries its commit's patch, the move of the branch onto the copies – `git -C <worktree> edit --onto=main` from its linked worktree, or with nothing else of its own the `reset --keep` or `git branch -f` a land names anyway; and the `--base` past them, and past every commit not the branch's own – a catch-up copy, one `main` dropped – that lands the branch's own commits that follow. Its own commits no step lands are named, with the `git -C <worktree> edit -d` taking the copies of what `main` dropped off it first. A copy a land of the branch brought, the branch holding that very commit when that land started – by its reflog, from the earliest copy that land made, or from `main`'s move before it where that first pick needed a resolution, a land under a name the branch had before a rename counting too – counts as landed whatever its patch, the difference that land's conflict resolution. Where the reflog cannot tell – expired, the branch deleted and made anew, or a value in that very second changing the answer – no fold of it is offered, only the `--base` past those copies, ending with nothing to land where nothing follows them, a difference of its own left to fold by hand. So a second land after a replay, the branch never moved onto the copies, refuses with that move, a retry after a land resolved by hand ends landed, and a fold made on the branch while a land of it ran is never read as landed. Only where `main` keeps no reflog does the branch's own answer, and where neither does the merge base – refused, naming a `--base` for either reading, where the span past it holds commits sharing author and subject with `main`'s, copies a rewrite left. The run says which fork it used and how it was found; `--base=<sha>` names one outright. Where `main` still sits below the branch's commits and on their fork, it fast-forwards by compare-and-swap from the tip it read. Otherwise the commits replay onto its tip in an isolated worktree, and a conflict pauses like any replay, with `--continue`, `--skip` and `--abort`. Either way the checkout comes along as after any landing, uncommitted edits merged onto what landed – where it can't, the run names the `--carry` that brings it along. The branch itself never moves – after a replay it still holds the originals, and the run names the command that points it at the copies, or for a branch checked out in another worktree, the one to run there – while the main worktree's branch stays as it is, as does one checked out nowhere landed into a linked worktree's branch, a catch-up likelier than its end, and the repository's default branch wherever it is checked out – `init.defaultBranch`, else a remote's `HEAD`, else `main` or `master` – the main line a land into another branch catches up from. A commit skipped at a stop, or emptied there by the resolution, is named as landed nowhere – by the replay's own record, never a patch id, so a commit whose context changed counts as landed – and then nothing that moves or deletes the branch is offered, as it alone still holds that commit – as for its own commits a `--base` leaves out below a fork `main` lacks, which `main` holds in no form – and a resumed land counts apart the commits made in its pause, one made at a stop then skipped among them; a run that lands nothing at all moves and journals nothing. A branch already landed, by ancestry, by patch id, by every commit's change and message on `main` or a copy a land of it took, or by a replay that comes out empty, or holding no commits of its own, ends `ok – … unchanged`, nothing landed. A target that moved meanwhile is refused, never overwritten, a merge commit in a replay's span is refused rather than flattened, naming the `--exec` merge that lands it where `main` still holds the fork, and `--undo`, or the raw `update-ref -m` printed beside it, takes the land back – `--undo` bringing the checkout back as it came, the raw one moving the ref alone. The rule reads `main`'s reflog, so past git's expiry of its unreachable entries a commit dropped long ago can come back – `--dry-run` lists what would land. A name is a branch first, whatever tag shares it; a tag, remote-tracking ref, SHA or revision such as `feat~1` lands as what it resolved to, said so, with no branch command offered for it.

## When it pauses

A conflict, an edit and a content split all pause the same way: the branch has not moved, the worktree the run is using holds the state to fix, and the trailer names it. Resolve or author there, stage what you changed, then `git edit --continue` – or `git edit --abort`, which has nothing to roll back. A cascade just repeats the loop, and `git edit --status` reprints the pause for a session that arrives without the original context. An edit or a content split re-reads the branch at `--continue`, carrying along a commit that landed while you worked – a conflict resolution, built on the old tip, refuses to apply over one instead, and keeps your resolution in the worktree. A rebase continued by hand in that worktree to its end lands as built, each stop it passed checked as one the run paused at – for a pause an older git-edit wrote, which kept no record of its stops, the stop it stands at as you resume – while one quit or aborted there lands nothing – `--continue` refuses, naming the picks the result lacks, and `--status` gives one aborted there that verdict too – bar an edit's replay, whose amend the pause keeps, so both name the way on: reset the worktree to that amend, then `git edit --continue`. So does one that lost a commit by hand, taken out of its todo or stepped over with a raw `git rebase --skip` where its change is not already there: a step gone empty, or a stop resolved to empty, goes with `git edit --continue`, and a replant's or a land's commit with `git edit --skip`. A fold whose own fixup was stepped over so folds nothing, and refuses as a resolution to the target's side does, your staging kept. A labeled caller's pause is its own: another `GIT_EDIT_ACTOR` label's `--continue` or `--abort` refuses unless `--allow-other-actor` says it is meant, and the resume journals under the pause's label. A repository holds one pause at a time: every mutating mode waits while another caller's is open, up to `--wait` (90 seconds by default), then refuses as in flight – `--commit`, `--exec` and `--undo` only where it is on the branch they move, `--undo` and a run on a pause of the caller's own refusing at once, an undo naming whose pause it is – and so does a run that reaches a pause of its own after a parallel session's took the slot, without waiting – removing the temporary worktree it made, as nothing there is authored yet. A run whose `-C` path a pause took as it started refuses once it holds the path, never resetting it – as does an edit, drop or squash past whose first look any pause on the repository was recorded, asked again once it holds its path or before it makes its temporary worktree – and a `--continue` decides on its pause as it stands once it holds the pause's worktree – one another resume took to a later stop meanwhile refuses, the pause kept.

A file whose committed bytes its attributes would store otherwise – one committed with CRLF line ends under `eol=lf`, say – reads as modified wherever git has just written it, though it is nobody's change. A run settles such a file in its worktrees as it starts, pauses and resumes, steps its replay past git's refusals over it, keeps it out of an edit's or a split's commit, and reads it in your checkout as the content it holds – never rewriting it there, so a replant's checkout update refuses over one, naming it. A real change left unstaged in a pause worktree still stops `--continue`, as git resumes from staged content only – the refusal names those files, with the `git add` and `git restore` that clear it.

Some steps need no answer from you. A reorder preserves the tree and a fold's result is the staged tree, so on the final step the right content is provable before anything is committed and `git edit` applies it itself, handing back only where the proof fails. What is left over is the genuinely ambiguous case: an intermediate reorder step rebuilds a state that never existed in history, which has to be authored rather than derived, and the pause says so – bar a file no later step touches, whose answer is the pre-op content again, which the pause names – unless that would leave the stop's own commit no change there, when the pause says so and names the way on the landing's refusal below would. And as a reorder only moves commits, one that ends on another tree refuses to land, naming the files – whether resolutions changed it or a clean replay did, a revert moved before what it reverts. Nor may a stop's resolution take in what a commit the new order puts after it changes: a commit moved below one it builds on, resolved to what it holds, empties that one into it, and the landing refuses, naming it and offering to squash the two instead – or, where other commits stood between them, the move right after it, as a placed `--commit` is offered `--after` that commit. A later commit that, rebuilt, still rewrites the line the moved one changes lands, its change rebased onto that one's. A rebase that stops with nothing to resolve, a hook's veto or a failed signature, pauses nothing: the run refuses with git's own error – a replant and a land too – while a resume's, an edit's replay of the commits after it among them, keeps its pause for a retry.

At a terminal a pause asks rather than exits – a terminal being stdin and stdout a TTY, with none of `CI`, `CLAUDECODE` or `GIT_EDIT_ACTOR` set, as a label marks an agent's run. `Enter` resumes it as `git edit --continue` would, staging each conflicted file you left without the markers git gave it – one it gave none, a binary's or a side's deletion, once you changed it or at a second `Enter` – `Escape` twice cancels it, and `q` leaves it for later, as `Ctrl-C` or a closed terminal does too. An arrow or function key counts as no answer, a key typed before a prompt showed answers none, and a prompt whose pause another run ended meanwhile acts on nothing. The worktree opens in the first GUI editor among git's editor sources (Sublime Text, VS Code, Cursor, Zed, a JetBrains IDE), `Space` re-opens it, and `GIT_EDIT_NO_AUTO_OPEN=1` turns that off – every editor starting in your own environment, git-edit's config pins out of it.

Once a run lands – an agent's as much as a terminal's, any mode – the checkout it started in comes along. Each file the move changed and nobody touched takes what landed. Uncommitted edits on one merge onto it, a file the merge leaves as it is never written. A merge that conflicts writes nothing – the edits may be another session's, whose file and index markers would disrupt – and leaves them as changes to what landed, naming the `git merge-file` that brings the markers in: at a terminal for you to run once you mean to resolve them, in an agent's run for the edits' owner – another session's are left to it, as its next commit of the file, by any route, is refused, naming that merge – until it holds what landed or its owner changed the conflicting lines. A file the run itself put or took whole, or folded as staged, holds your own later edits instead – a stage of it committed while the checkout holds the rest – so its index entry alone takes what landed. An untracked or ignored file standing where a file lands stays, as a change to it, and a binary or link no merge takes keeps the edits the same way, never as a staged revert. Staging a peer adds in a landed path's way, and a file a peer writes while the sync runs, stay as they are, the path named. A file staged and edited both stays as it was, named with the `--carry` whoever staged it runs before staging their part again, and a branch checked out twice has its other checkout named with the carry run there. What a move took out – a file it removed, or what a drop held – leaves the checkout too, named with the way back. Two runs landing a second apart don't interleave: each holds its checkout's sync from its ref move to the end, so the next one never reads a file this one is still writing. Where the sync can't run – a checkout halfway through a merge or a rebase, its index locked past the wait, the branch checked out elsewhere than the run started – the run names the one `git edit --carry=<old tip>` that brings it along once it can, never a restore. What a run leaves to do, a conflict's merge or that carry, prints last, right above the trailer – or above a commit line the last three keep, one line above the trailer then naming it. A run stopped by a second signal past its move, or killed there and journaled by a later run, names that carry too, and a carry partway through a rebase names the rebase, its step and the `git rebase --continue` or `--abort` that ends it.

The sync and `--carry` are one implementation, and each file comes along from the tip it was last brought to rather than from one base for all: a file still as an earlier tip had it takes what landed, one holding a landing's change merges from that landing's new tip – so a line a later landing took back leaves it – and one lacking a landing merges from that landing's old tip, never taking it back as an uncommitted edit; a file moved to its new name by hand takes its edits from the old name. The branch's journaled landings of the last 7 days tell this, and a path a sync left as it was – a conflict, staging, or no sync at all – is recorded with the tip it still sits on, in `git-edit-unbrought` in the checkout's git dir, until a later sync or carry brings it along. Where nothing tells – a peer's staging on the path, no journal, a binary – it merges from the one base a carry names. Every file still as its base had it goes in one two-tree merge, so a carry over thousands of files takes seconds.

## Verifying what a rewrite built

An `ok` trailer says the branch moved, not that the result works. A conflict resolution can be wrong with no marker left behind, and a fold can break a later commit that built on the old content:

```
git edit --amend-into=<sha> --verify='npm test' -- src/foo.js
git config edit.verifyCmd 'npm test'      # or as a standing gate on every operation
```

The command runs in the operation's own worktree – at the commit the mode authored, at the first one it rebuilt, at each one a move or reorder puts below a commit that came before it, at each commit a conflict resolution wrote, and at the new tip, `--verify-span` upgrading that to every rebuilt commit and `--no-verify-span` stepping a standing span back down for one run – before the compare-and-swap applies anything. That covers `--exec` too, whose command authors content nothing else has checked. A failure pauses with nothing applied – or, in the modes that have no pause, refuses outright, a split re-deriving its halves from its own worktree, `--exec` and `--commit` leaving their built commits addressable by SHA. Files left untracked in that worktree feed the check yet never land, so a gated resume refuses while it holds any that aren't ignored, `--exec` removes what its command left before the gate runs, and what the check itself leaves is removed after each run, so no run sees another's. Either way it answers the two questions a failure raises: it runs the same check at the commit the failing one replaces, so a failure that predates the rewrite is cleared rather than blamed on it, and it climbs to the first commit above that passes, which for a fold is the commit carrying what the folded code now needs earlier. From there `git edit --continue` re-verifies, `--no-verify --continue` applies the result anyway, and `--abort` cancels.

Pair it with `edit.worktreeLink`. A fresh worktree holds none of what the repo deliberately doesn't track, so `npm test` there would fail on a missing `node_modules` rather than on the commit – name those paths once and every temp worktree gets them symlinked in:

```
git config --add edit.worktreeLink node_modules
```

## Driving it from a script or an agent

Every run ends with a single status line, written as prose and anchored by `git-edit: <outcome>`:

```
git-edit: ok – <ref> moved <old-sha> → <new-sha>
git-edit: ok – <ref> unchanged[, <why>]
git-edit: ok – dry run built <new-sha> on <old-sha>, <ref> unchanged
git-edit: ok – carried <n> path(s) across <old-sha>..<new-sha>
git-edit: ok – no operation in flight
git-edit: ok – selftest <passed>/<total> passed[ – <what ran>]
git-edit: error – <reason>
git-edit: conflict – resolve in <worktree> (<files>); then 'git edit --continue' or 'git edit --abort'
git-edit: paused – <operation> <sha> in <worktree>; then 'git edit --continue' or 'git edit --abort'
git-edit: paused – verify failed at <sha> in <worktree>; output in <path>; then 'git edit --continue' (re-verify), '--no-verify --continue' (apply anyway), or 'git edit --abort'
git-edit: paused – mode change at <sha> in <worktree>; then 'git edit --continue' (re-check), '--allow-mode-change --continue' (apply anyway), or 'git edit --abort'
git-edit: paused – <operation> <sha> is <label>'s, not yours: leave it to that caller, or wait for it ('--allow-other-actor' takes it on)
git-edit: paused – a pause with no operation on record is <label>'s, not yours: leave it to that caller, or clear it with 'git edit --abort --allow-other-actor'
```

`<why>` says what left the ref as it was – a dry run, a branch already landed or with nothing to land, a run that landed or replanted nothing, or another run that moved it meanwhile, with its move.

**Dispatch on the trailer, not on the exit code.** A pipeline reports its last command's status, while the trailer is always the last stdout line: `grep -E '^git-edit: (ok|error|conflict|paused)'` decides what happens next, and the rest reads as text rather than as brittle key=value pairs.

**Keep the lines above it.** Blank-line padding is added only when stdout is a terminal, so a captured run comes out tight and even a `| tail -3` reaches the trailer and the line naming the commit the run touched. What the run leaves to do – a conflict's `git merge-file`, or the `--carry` where it couldn't bring the checkout along – prints right above them, a `Still to do` line above the trailer naming it where a commit line sits between. Above those sit the findings a rewrite reports about the *rest* of history – an edit's net history change, the commits a replay dropped as empty, a tip that differs from the staged result – and they move with the commit. A wrapper that forwards only the last line drops exactly those. What a gate did is one of them, so reach for a name rather than a line count: colour goes with the padding, a captured line starts at column zero, and `grep -E '^(Verif|Tip tree|Trees|Note: tip tree|git-edit:)'` answers what landed, what checked it and whether the trees came out as they were (`Tip tree identical ✓`, `Trees unchanged ✓`) or not (a fold's `Note: tip tree differs from the staged result`), wherever the summary sits – the trailer alone where the repo configured no gate at all, or where a failing one turned into the pause the trailer names. The verification line carries its own shortfall – `Verified 2 of 7 commit(s) … in 3s – 5 unchecked in between` – so that one grep cannot read a sampled run as a complete one, and it carries what the check took, with what a standing `edit.verifySpan` ran beyond the default tier, so the price of the tier reaches the next run's flags. A run that had a gate and declined it says so rather than going quiet like an ungated one, naming the check that never ran: `Verify skipped – --no-verify was passed, so \`npm test\` never ran`. So silence has one meaning left: this repo has no gate configured, which is a question for `git config edit.verifyCmd` rather than for any single run's output.

**Judge a pause by its trailer, then by the unmerged index** (`git -C <worktree> -c core.quotePath=false diff --name-only --diff-filter=U`, which names a non-ASCII file as `git add` takes it) – never by grepping for conflict markers. A verify or mode pause has nothing unmerged, an emptied step has nothing to resolve, an add/add or modify/delete places one side's file whole with no textual merge to mark, and a `rerere` replay arrives pre-filled. All four read as finished to a marker grep.

**Validate before staging, one file at a time.** "No markers left" is not validation – `--continue` refuses staged `<<<<<<<` blocks on its own, but semantically wrong content passes every marker check. A blanket `git add -A` chained into `--continue` stages whatever a broken resolver left behind before anything could look at it.

```
git edit --amend-into=<sha> -- <paths>       # exit 2 -> the conflict trailer names the worktree
git -C <worktree> -c core.quotePath=false diff --name-only --diff-filter=U
# resolve one file, validate it, then stage it singly:
git -C <worktree> add <file>
git edit --continue                          # dispatch on the fresh trailer, cascades repeat the loop
```

**Every move is attributed.** Each reflog entry names the operation – `git edit: amend-into <sha>`, `git edit: exec <oldest commit replaced>` – and, where `GIT_EDIT_ACTOR` holds a label such as an agent session's id, ends with ` [<label>]`, so a history viewer can say who moved the branch – any character but letters, digits, `_` and `-` mapped to `_`, and said so. The reflog never leaves the clone, so neither does the label. The undo journal keeps it too, as given – two labels mapping alike stay two callers there: every session and worktree of a repository shares that journal, so its last run can be a parallel session's on any branch, and a labeled caller's `--undo` refuses a run made under another label – or none – unless `--allow-other-actor` says it is meant.

**A run cut short leaves nothing unrecorded.** Signaled once its branch moved, a run finishes landing, and a second signal stops it with the move journaled and the index entries it stranded re-synced, its trailer naming them. Killed outright, its move stays in the branch's reflog alone: the next run, `--status` or `--undo` journals it from there and re-syncs those entries, so `--undo` and the whole-file guards see it, while `--status` names the temp worktree it left, which a run sweeps once it is 10 minutes old. A move with no journal lock left behind by a run that died – an older git-edit's, which journals it a moment after moving – is taken in only once 15 seconds old, so a live run's never is. Killed once its move is journaled but before its index re-sync, it leaves that re-sync to the next run or `--status` too, once – each landing marks its re-sync done, so a revert you stage by hand after one that finished stays staged, after a branch switch or an older git-edit's move too.

`man git-edit` carries the rest under SCRIPTING: the pause states in full, what `rerere` replays into a later conflict, and the snapshot-map recipe for a mechanical change across many commits, which belongs in a single `--exec` rather than in one fold per commit.

Worth putting in an agent's own instructions verbatim: *with `GIT_EDIT_ACTOR` set to your session's id, commit through `git edit --commit --text "…" -- <paths>` – or, where another session has uncommitted lines in the same file, through `--edits` with the replacements you made, files wholly yours still after `--` – and for any history-rewriting git command reach for `git edit` – for one it doesn't cover, `git edit --exec -- …` – so it can't disturb another session's working tree or take back what one landed.* The label is what tells another session's landing from your own – unlabeled, every unlabeled run counts as yours, and the guard lets a file take it back.

## ⚠ Warning: History Rewriting

Rewriting history changes the SHA of the commit you name and of every commit after it.
- Safe if: Those commits aren't pushed yet, or you're the only developer
- Risky if: Others have based work on them (branches, forks, etc.)

Which is why pushed commits are refused unless you pass `--allow-pushed`: landing the result then means a force-push (`git push --force`), and that disrupts everyone who has them.
